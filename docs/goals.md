# koala 목표 정리

## 목적 (2026-10-27, 사용자 확정)

브라우저 확장 형태로 browser use(AI가 브라우저를 직접 조작)를 구현하고, 이를 **QA 목적**으로 사용한다.

## 확인된 사실 (2026-10-27)

- QA 대상: 자회사의 웹서비스
- 범위: 해당 웹서비스에 대한 일반적인 QA
- 테스트 환경: 보통 목업 데이터가 들어간 상태에서 실행
- 진행 방식: 사용자도 이 분야가 처음이라, 먼저 벤치마킹을 하고 꼭 필요한 기능과 과한 기능을 가려낸 뒤 목표를 세운다

## 확정된 목표

### 핵심 방향 (2026-10-27, 사용자 확정)

- AI에 전부 맡기는 모델이 **아니다**.
- 흐름: **AI로 테스트를 실행·확인 → 확인된 테스트를 AI가 그대로 코드로 만듦 → 그 코드로 반복 테스트 구성**.
- 즉 AI는 테스트를 처음 확인하고 코드로 만드는 데 쓰고, 반복 실행은 코드가 맡는다.
- **등록**은 AI와 사람이 직접 한다. **동작**은 프로그래밍된 흐름대로 한다. (사용자 표현)
- **실행 위치**: 결과물은 Playwright 코드로 꺼내 **CI에서 실행**한다. (사용자 확정)
- 최적화와 속도 개선은 나중에 한다. **지금은 어디까지 가능한지 가능성 확인이 우선**이다. (사용자 확정)
  - 열린 질문: "사람이 직접 등록"이 사람의 클릭을 녹화하는 것인지, 코드·단계를 직접 쓰거나 고치는 것인지, 둘 다인지

### 벤치마크 재분류 (Claude의 추정, 확인 전)

- 꼭 필요로 올라옴: 시나리오 저장, 확인된 실행을 코드로 변환, 코드 재실행
- 업계 사례: Octomind, Exploratory Testing Agent, QA Wolf 가 Playwright 코드 내보내기를 제공

## 제약 (2026-10-27)

- **Claude API 키 없음. Claude Code 계정(구독)만 있다.** (사용자 확정)
  - 확장이 Claude API를 직접 부르는 구조(Nanobrowser 방식)는 쓸 수 없다.
  - AI 두뇌는 로컬 Claude Code가 맡아야 한다. 확장은 Claude Code와 로컬로 연결되는 손발 겸 기록기가 된다.
  - 후보 구조(Claude 추정):
    - (A) Claude Code → 로컬 MCP 서버 → WebSocket → 확장. 지시는 Claude Code 터미널에서 한다. Claude in Chrome과 같은 방식이다.
    - (B) 확장 사이드패널 → Native Messaging → 로컬 호스트가 `claude -p` 실행 → (A)의 MCP 도구로 조작. 지시는 사이드패널에서 한다.
    - (B)는 (A) 위에 한 겹 더 얹는 구조다.
  - **결정: 지시는 확장 사이드패널에서 한다 → 구조 (B).** (사용자 확정, 2026-10-27)

## 확장의 사용 모습과 가시성 (2026-10-27, 사용자 확정)

- 확장은 보통 **사람이 실제로 보면서** 쓸 것으로 예상한다.
- 그래서 **클릭, 입력, 포커스 같은 조작이 화면에서 잘 보여야** 한다.
- **상태와 데이터도 보여야** 한다. 그래야 사람과 AI가 같이 보면서 문제를 직관적으로 잡아낼 수 있다. (사용자 표현)
  - 열린 질문: 여기서 "상태·데이터"가 구체적으로 무엇인지(아래 제안은 Claude 추정)
- 다음 단계: 가용 도구(AI가 쓰는 조작·검증 도구)의 목록과 도구별로 보여 주는 방식을 명확히 한다.

## 확장 vs Playwright (2026-10-27 정리)

- 결론: 둘은 **서로 보완하는 관계**다. 확장은 **등록 도구**, Playwright는 **실행 엔진**으로 나누는 것이 koala의 "등록은 AI와 사람이 직접, 동작은 프로그래밍된 흐름대로"와 그대로 맞는다.
- 확장(`chrome.debugger`로 CDP 사용)은 조작·캡처 수준에서 Playwright와 거의 같은 저수준 능력을 가진다.
- 확장이 부족한 점:
  - 매 테스트마다 깨끗한 브라우저를 만들 수 없다.
  - headless 실행, CI, 병렬 실행이 안 된다.
  - 브라우저 엔진이 하나뿐이다.
  - 자동 대기, 재시도 검증, trace, 네트워크 모킹을 직접 구현해야 한다.
  - "디버깅 중" 안내 띠가 뜬다.
  - MV3 서비스워커는 일정 시간 뒤 잠든다.
- 확장이 나은 점:
  - 실제 사용자 브라우저와 세션(SSO 포함)을 그대로 쓴다.
  - 사람과 AI가 같은 화면에서 일하고, 중간에 사람이 개입하거나 이어받을 수 있다.
  - 사람의 조작을 자연스럽게 녹화한다.
  - 개발자가 아닌 QA 담당자도 설치해서 쓰기 쉽다.

## 대상 사이트

- 사이트별 정보(주소, 로그인 흐름, 마크업 특성, 데이터 출처, 발견한 결함)는 goals에 넣지 않는다. (사용자 지시)
- 공개 저장소이므로 사이트별 문서는 저장소 밖 로컬(`private/targets/<사이트>.md`, git 제외)에 둔다. 아래 기록의 화면 이름은 일반화했다. (2026-10-28 GitHub 공개 결정)
- 공통 운용 원칙: 대상 사이트는 사용자의 저장 세션과 분리된 **격리 브라우저(시크릿 모드에 해당)**로 접근한다. 계정은 `.env`에 둔다(git 제외). (사용자 지시)

## 가능성 판단 (Claude의 추정, 스파이크로 검증 전)

| 난이도 | 내용 | 예상 |
|---|---|---|
| 1. 단순 흐름 | 클릭·입력·이동을 Playwright 코드로 변환 | 높음. Playwright codegen, Chrome DevTools Recorder가 이미 사람 녹화로 하고 있음 |
| 2. 검증문 | AI가 "확인했다"는 것을 `expect()` 검증문으로 남김 | 중간. 무엇을 검증할지 AI가 고르는 것이 핵심 난제 |
| 3. 안정적인 대상 지정 | 재실행해도 깨지지 않는 locator(role, label, testid) | 중간. 대상 사이트의 마크업 품질에 좌우됨 |
| 4. 까다로운 화면 | iframe, 새 탭, 파일 업로드, canvas, 동적 데이터 | 낮음~중간 |
| 5. CI 재현성 | 로그인 상태, 목업 데이터 초기화 | 사이트 환경에 좌우됨. 목업 데이터라 유리 |

- 참고: 사람이 직접 녹화하는 등록은 기존 도구(Playwright codegen)로 이미 가능하다. 새로 확인해야 할 것은 **AI 실행 → 코드 변환** 쪽이다.

## 스파이크 1차 결과 (2026-10-27, 버림용 `spike/`)

확장 없이 핵심 가설 **"AI가 한 단계씩 조작하며 기록 → Playwright 코드로 변환 → AI 없이 재실행"**만 먼저 확인했다. 확장 역할은 `spike/step.mjs`(CDP로 떠 있는 Chrome 조작 + locator 기록)가, 변환은 `spike/generate.mjs`가 흉내 냈다.

| 확인 항목 | 결과 |
|---|---|
| AI 단계별 조작 + locator 기록 | 됨. 화면을 읽어 `data-testid`가 있으면 우선 사용, 없으면 CSS로 대체 |
| 기록 → `.spec.ts` 자동 변환 | 됨. 단순 매핑만으로 읽을 만한 코드가 나옴 |
| 생성 코드 재실행(화면 표시) | 통과 |
| 생성 코드 재실행(headless, 순차 3회) | 3/3 통과 |
| 생성 코드 재실행(headless, 동시 3개) | **1/3 통과**. 같은 계정 동시 로그인으로 세션이 끊김(추정) |
| 로그인 1회 + 세션 공유(`storageState`) 후 동시 5개 | 6/6 통과(설정 1 + 테스트 5) |

배운 점(범용):
- 변환기는 기록의 **로그인 단계를 떼어 내 공통 setup으로 빼야 한다**. 그대로 두면 CI 병렬 실행에서 깨진다.
- URL 검증은 끝까지 고정된 정규식(`/\/dashboard$/`)으로 만들어야 한다. 부분 일치는 `?redirect=` 같은 값에 잘못 걸릴 수 있다.
- 자동 생성 id가 섞인 testid(`datatable-v-0-93-…`)나 데이터 id가 박힌 testid(`…-remove-294821354305466377-btn`)는 재실행 시 깨진다. **locator 선택기가 이런 값을 걸러야 한다**.
- 쓰기 동작(등록·삭제)은 목업 데이터를 바꾼다. 쓰기 시나리오는 데이터 초기화 방법이 정해진 뒤에 다룬다.
- 아직 검증 안 한 것: AI가 **무엇을 검증할지** 스스로 고르는 품질(이번엔 화면 요소 표시 여부만), 확장·사이드패널·`claude -p` 연결.

## 스파이크 2차 결과: 사이드패널 연결 (2026-10-27)

구조: **사이드패널 ↔ (WebSocket) 로컬 호스트 `spike/host.mjs` → `claude -p`(구독 계정, `--resume`으로 대화 이어감) → koala MCP 도구 `spike/mcp-server.mjs` → 호스트 → 사이드패널이 현재 탭에서 실행**. API 키 없이 동작한다.

| 확인 항목 | 결과 |
|---|---|
| 사이드패널 지시 → Claude Code 실행 → 탭 조작 | 됨. 1차 지시 19초, 2차 지시 28초 |
| 이어지는 지시(대화 유지) | 됨. 2차 지시에서 다시 로그인하지 않고 이어서 진행 |
| 비밀값 보호 | AI는 `$KOALA_USER` 같은 이름만 보고, 실제 값은 호스트가 치환한다. 생성 코드에도 `process.env`로 남는다 |
| AI가 검증 항목을 스스로 고름 | 됨. 화면 섹션·입력란 위주로 9개를 고름(표시 여부만, 값 검증은 없음) |
| 기록 → 코드 → AI 없이 재실행 | 화면 표시 1회, headless 순차 3회 모두 통과 |

배운 점(범용):
- **확장의 클릭 방식이 Playwright와 다르다.** `el.click()`은 `li` 안의 링크까지 클릭이 전달되지 않는다. Playwright는 요소 중앙을 실제 마우스처럼 누른다. AI가 스스로 우회했지만, 기록에 불필요한 클릭이 남았다. 확장은 **`chrome.debugger`(CDP)로 실제 마우스 이벤트를 보내 Playwright와 똑같이 동작**해야 한다.
- 실패한 조작이 "성공"으로 기록될 수 있다(위 사례). 기록할 때 **조작 뒤 화면이 바뀌었는지** 확인하거나, AI가 단계를 정리하는 후처리가 필요하다.
- 시나리오의 **시작 URL을 첫 단계로 기록**해야 재실행 코드가 같은 곳에서 출발한다(호스트에 반영함).
- 서비스워커 대신 **사이드패널 페이지가 WebSocket을 쥐는 구조**가 단순했다. 다만 패널을 닫으면 연결이 끊긴다.
- 확장 로딩: 정식 Chrome 137+는 `--load-extension`을 막는다.
  - **정식 Chrome 156에서 확인 완료** (2026-10-27). 별도 프로필 + `--enable-unsafe-extension-debugging` + CDP `Extensions.loadUnpacked`로 자동 설치했다(`spike/launch-chrome.mjs`). 사이드패널 연결 → 지시 19초·검증 3개 통과 → 생성 코드 재실행 2/2 통과. 시작 URL도 자동으로 첫 단계에 기록됐다.
  - Chrome은 스토어 밖 확장을 "안전하지 않을 수 있는 확장 프로그램 — 출처를 확인할 수 없음"으로 표시하고 삭제를 권장한다. 사내 배포 방식(개발자 모드 수동 설치, 사내 정책 배포, 비공개 스토어 등록)은 나중에 정한다.
  - 사람이 직접 설치할 때: `chrome://extensions` → 개발자 모드 → 압축해제된 확장 프로그램 로드. 시크릿 창에서 쓰려면 세부정보에서 "시크릿 모드에서 허용"을 켠다.

## 스파이크 3차 결과: 가시성·상태·데이터 (2026-10-27)

사용자가 "우선 만들어줘"라고 해서 Claude가 정한 기본값으로 만들었다(Claude 결정):
- 속도는 "보통"이 기본이고 느리게·보통·빠르게를 고를 수 있다. 일시정지 버튼이 있다.
- 조작은 `chrome.debugger`(CDP)로 실제 마우스·키보드 이벤트를 보낸다.

**가용 도구 (14개)**

| 분류 | 도구 |
|---|---|
| 읽기 | `snapshot`(요소 + 표의 헤더·행 수·앞쪽 행), `screenshot`(AI가 이미지로 봄) |
| 이동 | `goto`, `back` |
| 조작 | `click`, `type`(한 글자씩), `select`(커스텀 드롭다운), `hover`, `press` |
| 검증 | `expect_visible`, `expect_text`, `expect_value`, `expect_count`, `expect_url` |

**보이는 것**
- 페이지 위:
  - 대상 강조 상자 + 동작 라벨("클릭", "입력: …")
  - 가상 커서 이동, 클릭 파동
  - 검증 결과(초록 ✓ / 빨강 ✗, 기대값과 실제값)
  - 상단 배너(이동, 키 입력)
- 사이드패널:
  - 상태줄: URL, 페이지 상태, 대기 요청(+장기 요청), API 오류 수, 콘솔 오류 수
  - 탭: 진행(단계 카드 + AI 설명), 네트워크(요청·응답 본문), 콘솔, 코드
  - 단계 카드마다 **그 조작으로 생긴 API 요청과 콘솔 오류**가 칩으로 붙는다.
  - 비밀값은 `•••••`로 가린다.
- AI도 같은 정보(단계별 요청·콘솔 오류)를 도구 결과로 받는다.

**확인 결과**
- 정식 Chrome 156에서 동작했다.
- 실제 마우스 클릭으로 바꾸자 메뉴 `li` 문제가 사라졌다. 생성 코드에서도 불필요한 클릭이 없어졌다.
- AI가 `expect_text`·`expect_count`로 내용까지 검증했다. 바뀔 수 있는 건수는 일부러 피했다.
- 생성 코드 재실행:
  - 15단계 시나리오: 2/2 통과
  - 10단계 시나리오: 1/1 통과
- **사람과 AI가 같이 보며 문제를 잡는 사례가 나왔다.** AI가 네트워크·화면 데이터를 보고 스스로 보고한 내용(사이트 한정 내용은 targets 문서에 둠):
  - 느린 API
  - 행 testid가 비정상인 표
  - 같은 행이 반복되는 표
- 입력란 포커스 실패를 오류로 드러냈더니, AI가 스크린샷으로 "직접 입력 스위치를 켜야 입력 가능"이라는 앱 동작을 알아내 우회했다.

배운 점(범용):
- 클릭 후 화면이 바뀌면 강조 표시가 옛 위치에 남는다. 클릭 직후에 숨겨야 한다.

사용자 제안: "최초 스캐닝은 느리게 정확하게 검토하면서 진행하고, 한번 지나간 경로는 차후에 명확하게 처리되도록 각 경로 정보까지 저장. PostgreSQL 그래프 방식으로."

  - 있음 → **재생 모드**: 빠르게. 알려진 경로를 AI에게 주고, snapshot 없이 이어 붙여 run 한 번으로 실행. 실패하면 그 지점부터 탐색.
  - 사이드패널 상단에 "탐색"·"재생" 표시가 붙고 속도가 자동으로 바뀐다.
- AGE 1.5 주의점:
  - 목록 내포(`[e IN p | …]`)가 없다. `nodes(p)`, `relationships(p)`로 받아 JS에서 엮는다.

## 테스트 데이터 정리 방향 (2026-10-27, Claude 제안 · 사용자 확인 전)

쓰기 시나리오(등록 등)를 반복 실행하면 데이터가 쌓인다. 정리 수단을 세 단계로 본다:

1. **테스트 데이터 이름 규칙**: koala가 만드는 데이터에는 식별용 접두어를 붙인다(예: `[koala] …`). 남은 데이터를 한 번에 찾아 정리할 수 있다.
2. **테스트별 뒷정리(teardown)**: 생성 코드가 등록 응답에서 id를 받아 두고, 테스트가 끝나면 같은 세션으로 API를 불러 되돌린다(회수 → 삭제). 화면에 회수 버튼만 있으면 화면 흐름으로 정리해도 된다.
   - koala는 이미 단계별 네트워크 응답을 수집한다. 그래서 등록 응답에서 id를 뽑아 teardown 코드를 생성할 수 있다(추정).
3. **환경 초기화**: CI 실행 전에 목업 DB를 정해진 스냅샷으로 되돌린다. 가장 확실하지만 대상 서비스 쪽(백엔드·인프라)의 협조가 필요하다.

권장(Claude 의견): 지금은 1+2, CI 정착 단계에서는 3.

## 테스트 데이터 정리 적용 (2026-10-27, 사용자 결정)

사용자 결정:
1. 이름 접두어는 `koala` 대신 짧게 **`[koa]`**.
2. 테스트별 뒷정리를 제안대로 진행한다.
3. 환경 초기화는 백엔드가 아직 없으니 하지 않고, 지금 권장 범위에서 최소한으로 한다.

**결과**
- AI 규칙: 데이터를 만들 때 이름 앞에 `[koa] `를 붙인다.
- 생성 코드:
  - 실행마다 `RUN` ID를 만든다. `[koa] …` 값과 그 이름을 찾는 검증에 ID를 붙인다.
  - `test.afterEach`에서 그 ID가 붙은 문서를 회수한다. 테스트가 실패해도 정리된다.
- `koa-sweep`: 남은 `[koa]` 문서(koa로 직접 만든 것 포함)를 일괄 회수한다.
- 대상 사이트에서 일반 권한으로 가능한 최소 정리는 회수다. 승인 전 문서는 삭제 API가 404를 돌려준다(사이트별 상세는 로컬 대상 문서).
- 등록 → 검증 → 회수 테스트: 2회 연속 통과. sweep 후 목록 화면이 원래 건수로 돌아왔다.

**생성 코드를 안정화하며 배운 점(범용)**
- 검증 글자 기준을 맞춘다. koa는 innerText로 확인하므로 생성 코드도 `toContainText(…, { useInnerText: true })`를 쓴다(Playwright 기본은 textContent).
- 그래프 경로에도 locator의 **일치 개수**를 남겨야 한다. 그래야 생성 코드가 strict 모드를 피하도록 `.first()`를 붙인다.
- 새로 만든 데이터를 **"n번째 행"으로 확인하면 깨진다**.
  - 그 이름을 가진 행(`filter({ hasText })`)으로 바꾼다.
  - 뒤따르는 같은 표의 행 검증도 그 행 안으로 좁힌다.
- 목록은 등록 직후 바로 반영되지 않을 수 있다(검색 색인 비동기 추정). 새 데이터 검증은 **새로고침하며 최대 20초 다시 시도**(`toPass`)한다.
- 저장된 그래프 경로만으로 테스트를 다시 만들 수 있다(`graph-to-recording.mjs`).

**알려진 문제**
- 재생 모드에 넘기는 "알려진 경로"가 190개까지 불어났다. 화면 사이에 순환이 생겨 가변 길이 경로 조합이 늘어났기 때문이다. 목적에 맞는 경로만 고르거나 엣지 단위로 요약해야 한다.
- 시나리오 시작 시 단계 수 표시(사이드패널)와 보관 파일의 단계 수가 1 다르다(보관 파일에는 시작 화면 이동이 포함됨).

## 데이터 제공·동기화 방향 (2026-10-27, 사용자 결정)

사용자 결정:
- 데이터 원본은 나중에 만들 **백엔드 서비스**에 둔다. 확장은 실시간 조회나 기본 설정에 의존하지 않고, **동기화해서 받아 저장한 사본**으로 동작한다.
- **테스트 데이터**는 전체를 받지 않는다. **테스트 하나 단위**로 받거나, 갱신해서 올리고 끝낸다.
- 크기가 작은 **설정 데이터**는 개인 확장에 저장한다. 테스트 계정 정보, 테스트 대상 서버, 서비스 정보, 프롬프트가 여기에 속한다.
- **버전 관리**로 업데이트를 받아 실행한다.
- **키체인(OS 비밀 저장소) 적용은 뒤로 미룬다.** 로컬 개발 환경이라 당장 중요하지 않다.

Claude 제안(구현 전):

| 종류 | 내용 | 확장 저장 위치 | 동기화 |
|---|---|---|---|
| 프로필 | 대상 서버, 서비스 정보(로그인 흐름·주의사항·이름 규칙), 프롬프트, 정리 규칙, 계정 | `chrome.storage.local` | 새 버전이 있으면 자동으로 받음 |
| 테스트 패키지 | 테스트 하나: 목적, 경로(그래프 일부), 생성 코드, 사전 조건 | IndexedDB(받은 것만) | 필요할 때 하나만 받기, 갱신하면 하나만 올리기 |

- 백엔드는 `id / 종류 / 버전 / 해시` 목록을 준다. 확장은 가진 버전과 비교한다.
- 올릴 때 기준 버전을 함께 보낸다. 그사이 다른 사람이 갱신했으면 충돌로 거절하고, 최신을 받아 다시 맞춘다.
- 직전 몇 개 버전은 남겨 되돌릴 수 있게 한다. 특정 버전에 고정할 수도 있다.
- 백엔드 전까지는 같은 API를 흉내 내는 임시 저장소를 쓴다(호스트가 git으로 관리되는 YAML 폴더를 제공).
- 계정 비밀번호: 당분간 로컬 설정에 평문으로 둔다(키체인은 보류). AI와 생성 코드에는 지금처럼 `$KOALA_PASS` 같은 이름만 노출한다.
  - 참고: 나중에 키체인을 붙인다면 macOS Keychain과 Windows 자격 증명 관리자를 `@napi-rs/keyring` 하나로 다룰 수 있다. CI는 환경 변수를 쓴다.

## 프로필 저장·동기화 구현 (2026-10-27)

- **임시 동기화 저장소** `spike/sync.mjs`:
  - `store/<종류>s/<id>.yaml`을 git으로 관리한다. API는 호스트에 붙어 있다.
    - `GET /sync/catalog`
    - `GET /sync/profiles/:id`
    - `PUT /sync/profiles/:id {base_version, data}` → 기준 버전이 다르면 409 충돌
  - 백엔드가 생기면 같은 API 모양으로 교체한다.
- **첫 프로필** (`profiles/<서비스>.yaml`): 대상 주소, 계정(이름·용도만), 사이트 지식 프롬프트, 정리 규칙.
- **확장** (`extension/profile.js`, manifest에 `storage` 권한 추가):
  - `chrome.storage.local`에 프로필, 활성 프로필, 개인 계정 값을 저장한다.
  - 패널을 열거나 호스트에 연결될 때 목록과 비교해 새 버전이면 자동으로 받는다. 직전 3개 버전은 보관해 되돌릴 수 있다.
  - 내가 고친 상태에서 저장소가 새 버전이면 덮어쓰지 않고 충돌로 표시한다. "저장소 버전 받기"로 해결한다.
  - 헤더의 프로필 칩 → 프로필 시트: 대상 주소, 계정(아이디·비밀번호는 이 확장에만), 사이트 지식, 동기화 / 변경 올리기 / 이전 버전.
- **실행 연결**: 지시와 함께 활성 프로필을 호스트로 보낸다(연결·변경 시에도 보냄).
  - AI는 프롬프트로 대상 서비스·계정 이름·사이트 지식을 받는다.
  - `$KOALA_USER`·`$KOALA_PASS`는 호스트가 프로필 계정 값으로 채우고, 없으면 환경변수를 쓴다.
- **확인**:
  - 내 수정 올리기: v1 → v2
  - 다른 사람이 먼저 v3을 올린 뒤 내 수정 올리기: 충돌로 거절
  - 저장소 버전 받기: v3
  - 저장소 v4: 자동으로 받고 타임라인에 알림
  - 개인 계정 값: 호스트로 전달됨, 저장소 파일에는 없음
- **주의**: 저장소에 쓸 때 YAML을 다시 생성하므로 파일 안의 주석이 사라진다(설명은 문서 필드로 옮기는 편이 낫다).

## 배포 전제: 각자 PC에 Claude Code (2026-10-27, 사용자 결정)

- 확장 사용자는 **각자 PC에 Claude Code가 설치·로그인돼 있다는 전제**로 진행한다. 없으면 경고한다.
- 구현:
  - 호스트가 켜질 때와 사이드패널이 연결될 때마다 Claude Code를 찾는다.
    - 찾는 순서: `CLAUDE_BIN` → PATH(`which`/`where`) → 흔한 설치 경로(macOS·Windows)
    - `claude --version`, `claude auth status`로 설치 여부와 로그인 상태를 확인한다.
    - 계정 이메일 같은 정보는 패널로 보내지 않는다.
  - 사이드패널 상단 경고(이때 "실행" 버튼이 막힌다):
    - 호스트 꺼짐 → `node host.mjs` 안내
    - Claude Code 없음 → 설치·`CLAUDE_BIN` 안내
    - 로그인 안 됨 → `claude auth login` 안내
  - 지시를 받았는데 Claude Code를 쓸 수 없으면 실행하지 않고 다시 확인해 알린다.
  - Windows에서 `claude.cmd`로 설치된 경우를 위해 shell 실행을 처리했다(실제 Windows에서는 미검증).
- 참고: 일반 확장처럼 설치만으로 끝내려면 AI 실행을 백엔드로 옮기거나(Claude API 키 필요), Native Messaging 설치 프로그램으로 호스트 자동 실행을 붙여야 한다(보류).

## QA 기본 지식 전달: 지식 문서 + 작업 폴더 (2026-10-27)

사용자 의도:
- Claude 기본 설정과 **서비스 QA 기본 지식**(서비스 목적, 주요 기능, 중점 방향)을 작성해 전달한다.
- koala의 "Claude 설정 보기"에서 관련 폴더를 열거나 프롬프트를 조회할 수 있게 한다.
- Claude를 호출할 때 이 파일들을 읽어서 동작한다.

장기 권장(사용자 승인):
- 작성은 git에서 한다(리뷰 가능).
- 원본은 동기화 저장소(나중에 백엔드)에 버전을 붙여 둔다.
- 각자 PC의 작업 폴더는 koala가 받은 내용으로 만드는 **사본**이다. 직접 고치지 않는다.

구현:
- **저장소의 새 종류 `knowledge`** (`store/knowledges/*.yaml`, `files:` 아래에 파일 이름과 내용):
  - `qa-common`: 공통 QA 원칙(검증 기준, 테스트 데이터, 보고 형식)
  - `<서비스>`: 서비스 지식 **초안**. 관찰 기반이고 "작성 필요" 표시가 있다. 담당자가 채워야 한다.
  - 프로필에 `knowledge: [qa-common, <서비스>]`, `claude: {model}` 필드를 추가했다(프로필 v3).
- **작업 폴더** `spike/workspaces/<프로필>/` (git 제외, `workspace.mjs`):
  - 들어 있는 것: `CLAUDE.md`(지식 파일을 `@`로 불러옴), `knowledge/<id>/…`, `.claude/settings.json`, `.koa/mcp.json`(절대 경로), `.koa/version.json`
  - 지식이나 프로필 버전이 바뀌면 다시 만든다. 이때 상주 세션도 새로 시작한다(대화는 이어지지 않음).
- **Claude 실행**: 작업 폴더에서 `--setting-sources project`로 실행한다. 사용자 개인 설정(훅·플러그인·스킬·권한 모드)은 읽지 않는다. 타임라인에 "지식 qa-common@v1 · <서비스>@v1"처럼 실행 버전을 남긴다.
- **사이드패널 "Claude" 버튼 → Claude 설정 시트**:
  - 작업 폴더 경로와 폴더 열기(Finder·탐색기)
  - 지식·프로필·Claude 버전, 실행 옵션
  - 파일별 탭
  - **실제 전달 내용**: ① koa 기본 규칙 ② CLAUDE.md(불러온 파일 펼침) ③ 프로필
- **확인**:
  - 도구 없이 질문했을 때 Claude가 지식을 읽고 답했다. "작성 필요"인 서비스 목적은 "모름"이라 하고, 관찰 내용은 추정으로 구분했다.
  - 실제 시나리오에서 공통 원칙의 보고 형식을 따르고, 서비스 지식의 중점 방향에 맞춘 다음 확인 항목을 제안했다.

발견한 문제(다음에 고침):
- 페이지가 바뀌는 단계(로그인 등)에서 일부 요청이 끝나기 전에 단계가 마무리되어, AI가 받는 요청 상태가 `pending`으로 남는다.
- 지식 문서는 아직 사이드패널에서 편집할 수 없다(보기만). 지금은 `store/knowledges/*.yaml`을 고치고 버전을 올려 게시한다.

## 계획(Plan)과 작성(Write) 분리 (2026-10-27, 사용자 결정)

- 테스트는 보통 케이스를 논의해 목록을 만든 뒤, 항목별로 테스트를 만든다. 그래서 **계획 작성과 테스트 작성을 나눈다**.
- **AI는 요청을 글로만 파악하지 않는다.** 실제 화면으로 이동해 무엇이 있는지 확인하고, 그것을 근거로 케이스를 만든다(사용자 강조).
- 계획 단계:
  - 쓸 수 있는 도구: 이동, 화면 읽기, 클릭(메뉴·탭·열기), 드롭다운 등
  - 데이터를 바꾸는 버튼은 확장이 차단한다. 입력과 검증 도구는 쓰지 않는다.
  - 결과는 근거 화면이 붙은 케이스 목록이다. 계획 문서로 저장하고 버전을 관리한다.
- 작성 단계: 계획의 케이스를 골라 수행하고, 테스트 코드를 만들어 케이스에 연결한다.

## 흐름 변경: 대화로 수행 → 이력으로 TDD·BDD → 고르기 → 반영 → 서버 전송 (2026-10-27, 사용자 결정)

- 계획/작성 모드 분리를 실제로 써 보니 중요하지 않았다. 사용자가 정한 흐름:
  1. 대화로 테스트를 수행한다. 예: "등록 화면 테스트해줘"
  2. 수행 이력을 기준으로 TDD·BDD를 생성한다.
  3. 목록에서 실제로 쓸 것과 뺄 것을 사용자와 결정한다.
  4. 반영한다.
  5. 서버로 전송한다.
- 구현:
  - 사이드패널 "이 수행으로 테스트 생성":
    - 같은 대화에서 AI가 수행 이력(조작·확인·네트워크·탭 순서)만 근거로 `save_tests`를 호출한다.
    - 결과는 흐름 지도, BDD 시나리오(Given/When/Then), TDD 케이스(입력·기대·검증, 정상/동등분할/경계값/예외/권한/접근성)다.
  - 초안은 저장하지 않고 사이드패널로 온다. 이번 수행 기록으로 만든 Playwright 코드도 함께 담긴다.
  - 테스트 목록 시트:
    - 흐름 / BDD / TDD / 코드 탭
    - 시나리오·케이스마다 사용 체크. 시나리오를 빼면 딸린 TDD도 빠진다.
    - **반영**(고른 것만 남김) → **서버 전송**(동기화 저장소 `store/suites/`, 버전 관리, 충돌 확인)
  - 확인:
    - 등록 시나리오 수행: 86.5초, 56단계, 탭 순서 측정 포함
    - TDD·BDD 생성: 89.6초, BDD 8 · TDD 18
    - 1개 제거 → 반영 → 서버 v1 저장: BDD 7 · TDD 17 + 코드
- 계획 모드에서 만든 장치(데이터 변경 요청 네트워크 차단, 버튼 차단)는 코드에 남아 있지만 지금은 쓰지 않는다.

## 서버 전송 전에 로컬에서 코드 생성·실행 (2026-10-27, 사용자 지적)

- 사용자: "서버로 전송하기 전에 로컬에서 해당 테스트에 대한 코드를 생성해야, 서버에서 그 코드를 환경에 맞게 셋팅해서 테스트 돌릴 것이 아닌가."
- 흐름: 수행 → TDD·BDD 생성 → 채택/미채택 → 반영 → **코드 생성(로컬 실행)** → 서버 전송
- 구현:
  - **코드 생성** 버튼: 채택된 시나리오·케이스만 같은 대화의 AI에게 보낸다. 녹화 기반 코드는 로케이터 참고용으로 함께 보낸다.
  - AI는 `save_code`로 Playwright 코드 한 파일(`tests/suites/<묶음 id>.spec.ts`)을 저장한다. 호스트가 바로 로컬에서 실행해 테스트별 결과를 돌려주고, AI는 실패를 고쳐 다시 저장한다. 검증을 빼서 통과시키지 않고, 앱 결함은 그대로 두고 보고한다.
  - 코드 규칙: 테스트 제목은 케이스 id로 시작, 상대 경로만 사용(주소는 `KOALA_BASE_URL`), 계정은 환경변수 이름만, 테스트마다 로그인부터, `[koa]` 데이터는 실행 ID를 붙이고 afterEach에서 정리.
  - 서버 전송은 지금 채택 목록으로 만든 코드가 있을 때만 켜진다. 채택이 바뀌면 다시 생성해야 한다.
  - 전송 내용: `code { runner, file, source, env(실행 환경이 채울 값), support(코드가 불러오는 정리 도우미), local_run(통과·실패와 테스트별 결과) }`. 서버는 env 값만 자기 환경에 맞게 넣고 그대로 돌린다.
- 확인(TDD 17건 채택):
  - 1차 실행 통과 14 · 실패 3 → 2차 통과 15 · 실패 2. 전체 468초, 입력 21만 토큰
  - 남은 실패 2건은 앱 결함 의심: 공백만 있는 제목으로 등록 버튼이 켜짐(TC-REQ-05-1), 대화상자를 Escape로 닫으면 포커스가 연 버튼으로 돌아오지 않음(TC-REQ-13-2)
  - 서버 v3 저장: 코드 18.7KB, env `KOALA_BASE_URL, KOALA_USER, KOALA_PASS`, `support/cleanup.ts` 포함

## BDD 시나리오도 코드로, 실행 과정 보이기 (2026-10-27, 사용자 요청)

- 사용자: "지금 코드는 tdd에 대한 것인데, bdd에 대한 것은?" → 그전에는 시나리오가 `test.describe` 묶음 이름으로만 쓰였다. 딸린 케이스를 모두 미채택한 시나리오(SC-REQ-07, 08)는 코드에서 빠졌다.
- 코드 구조:
  - `describe('BDD')`: 채택된 시나리오마다 테스트 하나. Given/When/Then 한 줄을 `test.step` 하나로 두고, 단계 제목은 시나리오 문장 그대로 쓴다.
  - `describe('TDD')`: 시나리오별로 케이스 테스트를 둔다.
  - 공통 동작은 함수로 묶어 두 묶음이 함께 쓴다.
- 호스트는 채택했는데 코드에 없는 id를 `save_code` 결과의 `missing`으로 AI에게 알린다.
- 결과에 `kind`(bdd/tdd)와 BDD 단계별 결과를 담는다. 코드 탭은 BDD 시나리오와 TDD 케이스를 나눠 보여 준다.
- **시간 제한 문제**:
  - 테스트가 30건으로 늘어 실행이 5분을 넘기자, MCP 서버의 `fetch`(undici)가 응답 헤더 대기 5분 제한에 걸려 `fetch failed`로 끊겼다.
  - 실행은 끝까지 돌았지만 AI는 결과를 못 받고 같은 코드를 다시 저장해 중복 실행이 생겼다.
  - 시간 제한이 없는 `node:http` 요청으로 바꿨다.
- **보이게** (사용자 요청 "보이게 작업을 해"):
  - 로컬 실행은 기본으로 브라우저 창을 띄운다(`--headed`, `KOALA_HEADED=0`이면 숨김).
  - 진행 리포터 `pw-progress-reporter.cjs`가 테스트 시작·단계·끝을 한 줄씩 내보낸다. 호스트가 읽어 사이드패널로 보낸다.
  - 코드 탭에 진행 막대, 지금 도는 테스트와 그 Given/When/Then 단계, 끝난 테스트를 바로 보여 준다. 타임라인에도 `[n/전체] 통과 · 제목`이 남는다.
- 확인: BDD 13 + TDD 17 = 30건, 통과 26 · 실패 4 (297초)
  - 결함으로 확인된 실패: SC-REQ-05, TC-REQ-05-1(공백 제목), TC-REQ-13-2(포커스 복귀). 결함은 대상 서비스 이슈로 넘겼다
  - SC-REQ-08: 401을 주입하면 오류 알림은 뜨고 데이터도 생기지 않는다. 하지만 세션 만료 안내나 로그인 이동이 없다. 기대 결과가 AI 판단이라 기획 확인이 필요하다.
  - 앞선 실행의 SC-REQ-13 실패는 코드 문제였다(실행마다 바뀌는 숫자가 든 testid). 이름과 접두어로 찾게 고쳐 통과했다.
- 실수 기록: 실행 중에 같은 계정으로 테스트를 따로 돌렸다. 같은 계정 동시 로그인은 먼저 로그인한 세션을 끊으므로 결과가 오염될 수 있다. 그래서 그 실행은 중단하고 다시 돌렸다.

## 태그 (2026-10-27, 사용자 결정)

- 사용자 결정:
  - 태그의 출처는 서버다. 서버가 아직 없으니 받았다고 가정한다(`store/tags/qa-tags.yaml`, 프로필 `tags: qa-tags`).
  - 태그는 시나리오와 케이스 둘 다에 붙인다.
- 태그 문서 구성:
  - 축(그룹): 실행 범위, 기능 영역, 우선순위, 검증 성격, 실행 조건, 상태
  - 축 속성: `exclusive`(축마다 하나만), `inherit`(시나리오에 붙이면 딸린 케이스가 물려받음, 지금은 기능 영역만)
  - 태그 속성: `description`, `apply_when`(AI 판단 기준), `auto`(규칙으로 자동 부여, 예: priority=high → `@p1`), `assign: human`(사람만), `requires: issue`
- 붙이는 순서: 자동 규칙(호스트) → AI 판단(`save_tests`의 tags, 기존 초안은 `save_tags`) → 사람(테스트 목록에서 추가·제거, `@known-defect`는 이슈 번호 필수)
  - AI는 목록 밖 태그와 사람 몫 태그를 붙일 수 없다. 축마다 하나만인 축에서는 자동 규칙이 이긴다.
- 검사(패널): 목록에 없는 태그, 하나만인 축의 중복, 이슈 없는 `@known-defect`. 하나라도 있으면 코드 생성과 서버 전송이 막힌다.
- 코드: BDD는 `test(id, { tag })`, TDD는 `describe(시나리오, { tag: 물려줄 태그 })` 안에 `test(케이스, { tag, annotation: issue })`
  - 이슈 번호는 태그가 아니라 annotation이다.
- 확인 방법: 실행 전에 `--list`(몇 초)로 빠진 id와 태그 불일치를 먼저 본다. 있으면 실행하지 않고 AI에게 돌려준다.
  - Playwright JSON은 태그를 `@` 없이 내므로 붙여서 비교한다.
- **태그만 바뀌면 다시 실행하지 않는다** (사용자: "테스트를 왜 계속 돌리는가"):
  - 호스트가 코드의 `{ tag, annotation }`만 바꿔 끼우고 목록 검사만 한다(약 2초). 지난 실행 결과를 그대로 쓴다.
  - 그전에는 태그만 바꿔도 AI가 코드 전체(약 40KB)를 다시 쓰고(2~3분) 30건을 다시 돌렸다(5분).
  - 유효한 실행 결과가 없으면(중단·오류) 서버 전송은 켜지지 않는다.
- 이번에 드러나 고친 것:
  - 호스트가 오류로 죽으면 Claude 프로세스가 남아 새 호스트에 저장을 보냈다. 이제 호스트가 끝날 때 Claude와 테스트 실행을 함께 끝낸다. 코드 생성 지시 없이 온 저장은 거부한다.
  - 사이드패널 "실행 중"이 굳는 문제: 다시 연결되면 푼다.
  - 중지가 AI만 멈추고 테스트 실행은 두던 문제: 함께 멈춘다.
- 결과: AI 태그 제안 40초(브라우저 조작 없음). 알려진 결함 3건(SC-REQ-05, TC-REQ-05-1, TC-REQ-13-2)에 `@known-defect`와 이슈 번호를 붙였다.
- 남은 것: AI가 다시 쓴 코드에서 SC-REQ-10·TC-REQ-10-1이 실패했다.
  - 원인은 코드 오류다. 목록 확인을 표의 첫 줄로 하는데, 그 줄이 보이지 않는 줄이다.
  - 사용자 요청으로 실행을 멈췄기 때문에, 지금 코드에는 유효한 실행 결과가 없다.

## 테스트 추가: 기존은 그대로, 새 것만 덧붙이기 (2026-10-27, 사용자 결정)

- 세션 비우기: 대화 맥락만 지우고 다음 지시에서 새 `kaa-N`으로 시작한다. 수행 기록은 유지한다.
- 참고: 세션을 비워도 경로 그래프에 쌓인 단계(오류 주입·검증 포함)는 재생 안내로 AI에게 전달되므로, AI가 이전 결과를 추론할 수 있다.

**디자인**
- TDD 표와 예외 점검표를 BDD처럼 한 장 카드로 바꿨다(머리줄 + 라벨/내용 줄).

## 역할과 계정: 어떤 권한으로 테스트했는지 남기기 (2026-10-27, 사용자 결정)

- 배경(사용자 지적): 지금까지는 관리자 계정 하나로 테스트해 모든 메뉴에 접근할 수 있었다. 실제로는 일반 사용자·운영자 등 역할마다 메뉴와 권한이 다르고, 다른 서비스에는 역할이 더 많다. 어떤 계정으로 테스트했는지가 테스트의 일부다.
- 원칙: **역할**과 **계정**을 나눈다.
  - 역할: 서비스가 정한 권한 종류(key·이름·설명). 프로필에 둔다. koala는 역할 목록을 고정하지 않고 프로필이 정한다(태그처럼 나중에 서버가 내려줌).
  - 계정: 역할에 붙는 실제 로그인. 프로필에는 key·역할·이름표만 있고, 아이디·비밀번호는 각자 확장에만 저장한다. 환경변수 이름은 `<계정 key>_USER` / `_PASS`(예: `KOALA_ADMIN_USER`).
  - `default_role`: 역할을 말하지 않은 테스트가 쓰는 역할.
- 1단계(구현):
  - AI는 역할 목록(설명·계정 이름·값 입력 여부)을 받는다. 사용자가 역할을 말하면 그 계정으로, 아니면 기본 역할로 로그인하고, 로그인 전에 어느 역할인지 말한다.
  - 호스트는 아이디 입력란에 `$<계정>_USER`를 넣는 것으로 지금 로그인한 역할을 안다. 헤더 밴드에 역할 배지로 보이고, 기록의 각 단계에 `role`로 남는다. 상태 파일에 저장되어 재시작해도 이어진다. 기록까지 비우면 지운다.
  - 시나리오에 `as`(수행 역할)가 붙는다. AI가 적은 것 → 이번에 로그인한 역할 → 기본 역할 순. 케이스는 시나리오의 역할을 따른다.
  - 태그: 프로필 역할로 '실행 역할' 축(`@role-<key>`, 하나만, 케이스가 물려받음)을 덧붙여 `as`에서 자동으로 붙인다. 서버 공통 태그 문서에는 넣지 않는다(서비스마다 역할이 다르므로).
  - 코드: 파일 위쪽 `ACCOUNTS = { ADMIN: { user: process.env.KOALA_ADMIN_USER!, … } }`, `login(page, '<역할>')`. 환경변수 이름을 글자 그대로 적어 서버가 필요한 값을 알 수 있게 한다.
  - 호환: 역할 전 코드의 `KOALA_USER`·`KOALA_PASS`는 기본 역할 계정으로 본다. 기본 역할 계정에 값이 없으면 예전 `.env`의 `KOALA_USER`를 쓴다. 확장에 저장된 옛 계정(`KOALA`) 값은 기본 역할 계정으로 옮긴다.
  - 역할이 적혀 있지 않은 옛 시나리오는 카드에 '관리자 · 기본'처럼 점선 배지로 보이고 기본 역할로 돈다.
- 2단계(예정): 권한 점검(같은 화면을 역할마다 다르게 기대: `roles: { ADMIN: 허용, MEMBER: 거부 }`), 여러 사람이 이어 하는 흐름(`actors: { 작성자: MEMBER, 승인자: OPERATOR }`), 한 역할에 계정 여럿(병렬 실행·동시 로그인 회피).

## 역할 문서와 여러 역할 한 번에 수행 (2026-10-28, 사용자 결정)

- 사용자 결정:
  - 서버는 **역할과 역할별 기본 계정**까지만 내려준다. 각 사용자는 계정을 자기 것으로 바꿔 쓸 수 있다.
  - 메뉴 권한은 서비스마다 설정 방식이 달라 서버가 주지 않는다. **AI가 역할마다 직접 찾는다.**
  - 사용자는 프로필을 고르고, 계정이 여럿이면 한 번에 모든 역할로 테스트하고 싶어 한다.
- 역할 문서(`kind: role`, 예 `store/roles/example-roles.yaml`): `default_role`, 역할마다 key·이름·설명·기본 계정(`account: {user, pass}`).
  - 프로필은 `roles: <역할 문서 id>`로 가리킨다(프로필 v6). 확장은 동기화할 때 역할 문서를 늘 새로 받는다.
  - 서버가 없는 지금은 임시 서버(sync.mjs)가 기본 계정을 `spike/.koa/server-accounts/<id>.yaml`(git 제외)에서 채워 내려준다. 비밀값을 저장소에 두지 않기 위해서다. 이 파일이 없는 설치본은 기본 계정이 비어 각자 계정을 넣는다.
- 계정: 역할마다 `KOALA_<역할>`(환경변수 `KOALA_ADMIN_USER` 등). 내가 바꾼 계정이 있으면 그것, 없으면 서버 기본 계정. 프로필 시트에 출처(서버 기본 / 내 계정 / 없음)와 '기본 계정으로' 버튼.
- 역할 범위: 입력창 아래 역할 칩으로 이번 지시를 수행할 역할을 고른다. 기본은 계정이 있는 역할 모두, 계정 없는 역할은 고를 수 없다.
  - 여럿이면 AI가 차례로 수행한다: `clear_login`(대상 사이트 쿠키·저장소 지우기) → 그 역할로 로그인 → 수행. 첫 역할은 끝까지, 다음 역할은 권한이 갈리는 지점만.
  - 메뉴 권한 찾기: 로그인 직후 보이는 메뉴, 메뉴·주소 직접 접근 결과(열림/돌려보냄/권한 없음), 버튼 활성, 401·403 응답. 확인한 것은 expect_*로 남기고 역할 × 항목 표로 요약한다.
- 초안: 여러 역할로 확인한 시나리오는 복사하지 않고 `roles: { ADMIN: "허용", MEMBER: "거부: …" }`로 역할별 기대를 적는다. 카드에 역할 배지(✓ 허용 / ✕ 거부). 역할 태그가 역할마다 붙는다(실행 역할 축은 여럿 가능, AI는 고르지 않음).
- 코드: 역할별 기대가 있는 시나리오는 역할마다 테스트를 만든다(`<id> [ADMIN] …`, 역할 태그는 그 역할 하나). 결과는 실패한 역할을 먼저 보인다. 코드 검사는 역할 태그를 '목록 안의 것, 하나 이상'으로 본다.
- 하지 않은 것: Playwright 역할별 프로젝트·로그인 상태 재사용(storageState). 지금은 테스트마다 자기 역할로 로그인한다.

## GitHub 공개와 호스트 보안 (2026-10-28)

사용자 결정: 저장소를 GitHub public으로 공개하고 개발도 GitHub로 완전히 옮긴다. 공개 저장소는 새 기록 1개로 시작하고, 작성자는 GitHub noreply 메일로 한다.

- **호스트 접속 제한**: 127.0.0.1에만 열어도 사용자가 연 아무 웹 페이지나 WebSocket·POST로 호스트에 붙을 수 있었다(계정 값 수신, 코드 실행, 대상 사이트 조작). 공개하면 접속 방법이 드러나므로 막았다.
  - Host 헤더가 127.0.0.1/localhost가 아니면 거절(DNS 리바인딩)
  - 브라우저 요청은 koala 확장 출처만. 확장의 GET은 Origin 없이 `Sec-Fetch-Site: none`으로 오므로 그것만 허용
  - MCP 서버 같은 로컬 프로세스는 `.koa/host-token`(0600)을 헤더로 낸다
- **계정 값은 대상 서버 화면에만 입력**: 페이지 글에 속은 AI가 다른 사이트 입력란에 `$KOALA_*_PASS`를 넣지 못하게 확장이 막는다.
- **대상 사이트 정보는 저장소 밖**: 동기화 저장소를 둘로 나눴다. `store/`는 공용 예시(공통 지식, 태그, 예시 프로필·역할), `.koa/store/`는 이 PC의 문서(대상 서비스 프로필·지식, 보낸 테스트 묶음). 같은 id면 `.koa/store/`가 먼저이고, 쓰기는 언제나 `.koa/store/`로 간다. 사이트별 메모는 `private/`(git 제외), 생성된 테스트(`spike/tests/`)도 git에서 뺐다.
- **배포**: 설치·업데이트를 GitHub 릴리즈 기준으로 바꿨다(1분마다 확인. 최신 태그는 웹 주소 이동으로 알아내 API 한도를 쓰지 않고, 새 버전일 때만 API로 노트를 받는다).

## 도메인별 작업 데이터와 시작 URL (2026-10-28)

사용자 결정:
- 로컬에 저장하는 작업 데이터는 도메인 기준으로 나누고, 그 도메인에서만 불러온다. 도메인은 프로필 대상 주소가 기본이다.
- 범위는 작업 데이터 전부: 수행 기록, Claude 세션(kaa-N), 타임라인, 테스트 초안·목록.
- 어느 도메인인지는 고른 프로필로 정한다. 대상 탭이 그 도메인이 아니면 실행을 막는다.
- 도메인 단위는 호스트 이름만(포트·프로토콜은 구분하지 않는다).
- 시작 URL(Starting URL)은 프로필에 하나(`target.start_url`). 새 수행 기록은 거기서 출발하고 생성 코드도 거기서 시작한다.

구현:
- 호스트: `.koa/domains/<호스트>/`에 `state.json`(대화 id·세션 이름·수행 기록·현재 화면·로그인 역할), `recording.json`, `recordings/`, `drafts/`. 전체 `.koa/state.json`은 지금 도메인과 세션 번호(kaa-N, 도메인을 넘어 이어 센다)만 둔다. 예전 데이터는 기록의 첫 주소 도메인으로 옮긴다.
- 확장: `timeline@<도메인>`, `suite@<도메인>`. 예전 타임라인은 처음 불러온 도메인으로, 예전 초안은 그 초안 프로필의 도메인으로 옮긴다.
- 도메인은 확장이 정해 호스트에 보낸다. 대상 주소를 고치는 도중(입력 중)에는 바뀌지 않고, 입력을 마치거나(포커스가 빠질 때) 프로필을 바꿀 때 바뀐다. AI 작업 중에는 다른 도메인으로 바꾸지 않는다.
- 시작 URL이 대상 주소와 다른 도메인이면 쓰지 않고 프로필 시트에 경고를 띄운다.

## 배포 서버와 프로필 만들기 (2026-10-28)

사용자 결정:
- '서버 전송'은 서버 정보가 없으면 비활성화한다. 배포 서버는 프로필에서 설정한다(`deploy.url`).
- 로컬에서도 프로필을 새로 만들 수 있게 한다. '변경 올리기'·'이전 버전'은 오해하기 쉬우니 이름과 동작을 분명하게 한다.

구현:
- 배포 서버는 임시 동기화 저장소와 같은 모양의 API를 쓴다고 가정한다(`PUT <서버>/sync/suites/<id>` { base_version, data } → 문서 | 409 { current }). 주소가 이 호스트면 `.koa/store`에 바로 쓴다. 인증은 아직 없다(배포 서버 API가 정해지면 붙인다).

## 프로필은 서버에서 받기만 (2026-10-28)

사용자 지적: '서버에 저장'이 실제로는 이 PC의 임시 저장소에 쓰고 있었다. 원칙은 서버에서 받는 것이었다.

사용자 결정(Claude 제안 채택):
- 서버 프로필은 받아서 쓰기만 한다. 패널에서 고치거나 올리지 않는다('저장소에 저장'·'되돌리기' 제거). 서버에 새 버전이 오면 그대로 받으므로 충돌도 없다.
- 사람마다 다른 값만 '내 설정'으로 이 확장에 둔다: 계정(이전과 같음), 시작 URL. 대상 주소·배포 서버·지식·태그·역할·사이트 지식·정리 규칙은 서버 값으로 고정한다.
- 서버에 없는 사이트는 '이 PC 전용 프로필'로 만든다(확장 저장소에만, 고치기·지우기 가능). 팀과 나누려면 서버에 등록한다.
- 프로필 내용 변경은 서버 쪽에서 한다. 공유 서버가 생기기 전까지는 임시 저장소의 YAML 파일을 고친다.

## 테스트 초안은 대화로 만든다 (2026-10-28)

사용자: 대화하다가 '이 수행으로 테스트 생성' 버튼을 누르는 게 불안하고, 불필요해 보인다.

- 버튼을 없앴다. 사용자가 "지금까지 한 걸로 테스트 만들어줘"라고 하면 AI가 `make_tests`(범위 메모 포함)를 부르고 응답을 끝낸다. 호스트는 그 응답이 끝난 뒤 예전 버튼과 같은 초안 만들기 작업(수행 기록 요약·태그 목록·진행 카드)을 시작한다.
- 말뜻은 AI가 가린다. "○○ 테스트해줘"는 수행 요청이고, 만들어 달라는 뜻이 분명하지 않으면 먼저 묻는다. 수행 기록이 없으면 make_tests 가 거절하고 AI가 먼저 수행하라고 알린다.
