# 세트 단위 데이터 관리 — 설계

작성 2026-10-29. 상태: 구현됨 (브랜치 sets-data).

## 왜

지금 koala는 작업 데이터를 **도메인**(프로필 대상 주소의 호스트 이름) 기준으로 나누고, 일부는 **프로필 id** 기준으로 나눈다. 실제 일의 단위는 그 어느 쪽도 아니다.

실제 단위는 **세트**다. 세트는 대상 서비스·버전에 목적을 붙인 점검 단위다.

- 예: `서비스A 2.0 취약점 점검`, `서비스A 2.0 보안성검토`, `서비스A 3.0 poc-1`
- 같은 서비스(같은 도메인)에 세트가 여럿 생긴다. 도메인 기준이면 '취약점 점검'과 '보안성검토'의 작업이 한곳에 섞인다.
- 한 세트에 테스트가 40~100개 생긴다. 서비스 하나에 다 넣기엔 많아서 목적별로 나눈 것이 세트다.
- 세트는 원칙적으로 서버에서 받는다(프로젝트 또는 그 하위 정보). 받는 정보의 종류는 늘어날 수 있다. 세트는 n개를 받는다.

그래서 데이터를 **세트별로** 관리한다.

## 사용자가 정한 것

- 데이터의 기준은 세트다. 세트를 고르면 그 세트의 데이터만 보인다.
- 사이드패널 위쪽에서 고르는 단위가 프로필에서 **세트**로 바뀐다. 세트를 고르면 대상 사이트·역할·지식이 따라온다. 프로필은 세트 안의 정보다.
- **대상 사이트는 세트당 하나**다.
- 테스트는 대부분 AI에게 요청해서 만들어 간다. 지금 범주는 고객 요구사항, 일반 기능.
- 세트 안 테스트의 분류는 **태그**로 한다. 태그 기준은 아직 정하지 않았다.
- 서버 프로필은 받기만 한다(이전 결정 유지). 시작 URL·계정만 내 설정이다.
- 서버에서 세트 정의가 바뀌면 **알림만 주고, 사용자가 받기를 누른다**(자동으로 덮어쓰지 않는다).
- 서버로 보내는 것은 아직 방향만 있다. 데이터 형태가 정의되면 그 형태(파일이든 JSON이든)로 보낸다.

## 목표

1. 세트 하나의 데이터(받은 정의, 테스트, 코드, 실행 결과, Claude 세션, 수행 기록, 로그)가 한곳에 모이고, 다른 세트와 섞이지 않는다. 같은 도메인의 세트끼리도 섞이지 않는다.
2. 세트를 지우거나 다른 PC로 옮기는 일이 폴더 하나(+확장 저장소의 그 세트 키)로 끝난다.
3. 서버에서 받은 것 / 내 설정 / 내가 만든 작업 데이터 / 서버로 보낼 것의 경계가 저장 위치로 드러난다. 나중에 실제 서버로 바꿀 때 받는 쪽만 바꾸면 된다.
4. 세트당 테스트 40~100개를 다룰 수 있다: 태그로 걸러 보고, 골라 실행하고, AI에게 더 만들어 달라고 해서 쌓아 간다.
5. 분류(태그 체계)가 바뀌어도 저장 구조를 옮기지 않는다.

## 하지 않는 것

- 실제 서버 API 만들기. 지금처럼 로컬 저장소(`.koa/store/`)로 흉내 낸다.
- 비밀값 키체인 저장(사용자가 뒤로 미룸).
- 태그 체계 확정.
- 세트 하나에 대상 사이트 여러 개.
- 서버로 보내는 데이터의 형태 확정. 파일일지 JSON일지는 데이터 형태가 정의된 뒤 정한다(아래 '보낼 것').

## 실패로 보는 것 (기능은 돌아도)

- 같은 도메인의 두 세트 사이에서 테스트·세션·기록이 섞이거나, 한쪽을 고르면 다른 쪽 것이 보인다.
- 기존 사용자의 작업 데이터(수행 기록, 테스트 목록, 코드, 실행 결과)가 업데이트 후 사라진다.
- 서버에서 받은 정의를 사용자가 패널에서 고칠 수 있게 된다(받기만 원칙 위반).
- 공개 저장소에 대상 사이트 정보가 들어간다(세트 이름 예시 포함).
- 테스트 100개짜리 세트에서 AI가 테스트 하나 추가하려고 코드 전체를 다시 써서 기존 테스트가 깨진다.

## 영역

| 영역 | 무엇 | 세트별? |
|---|---|---|
| 서비스 | koala 자체: 호스트 토큰, 실행 설정(`.env`), 화면 설정, 세션 번호(kaa-N), 공용 예시(`store/`), `~/.koala/` | 아니오 |
| 받은 것 | 세트 정의: 대상 프로필, 역할(+기본 계정), 지식, 태그, 계획, 앞으로 늘어날 정보 | 예, 읽기 전용 |
| 내 설정 | 세트별 시작 URL, 내 계정, 역할 범위 선택 | 예 |
| 작업 | 테스트 목록, 코드, 실행 결과, Claude 작업 폴더·세션, 수행 기록·보관본, 로그, 타임라인 | 예 |
| 보낼 것 | 서버로 보낼 테스트(배포 서버). 형태 미정 | 예 |

## 저장 구조

```
spike/.koa/
  state.json                 서비스: 지금 세트 id, 세션 번호(kaa-N)
  host-token
  store/                     서버 흉내(받는 쪽 원본). sets/<id>.yaml 추가
  sets/<세트 id>/
    set.json                 받은 세트 정의의 스냅숏(버전·받은 시각·출처: server | local)
    received/                세트가 참조하는 문서들의 스냅숏(역할, 지식, 태그…) — 읽기 전용
    secrets/                 서버가 준 기본 계정(0600). 로그·패널 표시에 값이 나가지 않음
    tests/
      tests.json             테스트 목록(BDD·TDD, 태그, 채택, 이슈) — 이 세트의 원본
      code/*.spec.ts         테스트 코드
      results/               실행 결과(테스트별 마지막 결과, 실행 이력)
    work/
      claude/                Claude 작업 폴더(cwd). 세션은 이 경로에 묶인다
      state.json             Claude 세션 id, 수행 기록, 현재 화면, 로그인 역할
      recordings/            기록 보관본
      logs/<날짜>.jsonl       작업 로그(30일)
    outbox/                  서버로 보낸 마지막 내용과 그 버전(형태 미정)
spike/store/                 공용 예시(git). 세트 예시 하나 추가
확장 저장소                   activeSet, setPrefs[세트](시작 URL·계정·역할 범위), timeline@<세트>, 받은 세트 목록 캐시
```

- 받은 것은 **받을 때 스냅숏**으로 세트 폴더에 둔다. 서버의 세트 정의나 그것이 참조하는 문서(예: 공통 QA 지식, 태그)가 바뀌어도, 사용자가 받기를 누르기 전까지는 세트가 쓰던 판으로 돈다.
- 새 판이 있는지는 지금처럼 주기적으로 본다. 세트 버전이 오르거나 참조 문서의 버전이 바뀌면 패널에 **새 버전 있음**과 바뀐 것(예: 태그 2개 추가, 역할 변경)을 보여 주고 **받기** 버튼을 둔다. 받으면 스냅숏을 바꾸고 Claude 작업 폴더를 다시 만든다. AI 작업·테스트 실행 중에는 받지 않는다.
- 받은 뒤 기존 테스트의 태그가 새 태그 목록에 없으면 지우지 않고 지금처럼 태그 문제로 표시한다.
- 서버가 준 기본 계정(`secrets/`)도 받기를 누를 때 함께 바뀐다.
- 도메인은 저장 키에서 빠진다. 세트 정의의 대상 주소에서 계산해 **탭이 맞는지 확인**하는 데만 쓴다(지금의 멈춤 → 이동/그래도 진행 흐름 유지).
- 테스트 목록의 원본을 확장 저장소에서 **호스트 파일(`tests.json`)로** 옮긴다. 테스트 100개에 코드·결과까지 확장 저장소(약 10MB 한도, `unlimitedStorage` 없음)에 두기엔 크고, 한 세트를 폴더 하나로 다루려면 호스트 쪽에 있어야 한다. 패널은 호스트에서 받아 보여 주고, 바꾼 것을 호스트로 보낸다.
- Claude 작업 폴더가 세트 폴더 안으로 들어오므로, 세션 id와 작업 폴더가 같은 세트에 묶인다(지금은 세션은 도메인, 작업 폴더는 프로필이라 어긋날 수 있다).

## 세트 정의 (받는 형식)

서버 흉내 `.koa/store/sets/<id>.yaml`:

```yaml
id: svc-a-2.0-vuln
name: 서비스A 2.0 취약점 점검
version: 3
profile:            # 대상 사이트 하나. 지금 프로필 문서의 내용
  target: { base_url: https://svc-a.example, start_url: https://svc-a.example/login }
  deploy: { url: … }
roles: svc-a-roles  # 참조: 받을 때 received/ 로 풀어 넣는다
knowledge: [qa-common, svc-a]
tags: [qa-tags, svc-a-req]   # 세트마다 다른 태그(예: 고객 요구사항 번호)를 둘 수 있다
```

- 새 정보 종류가 늘어나면 키를 추가하고 `received/<종류>/`에 스냅숏한다. 모르는 키는 그대로 보관한다(지우지 않는다).
- 서버에 없는 세트는 패널에서 **이 PC 전용 세트**로 만든다(지금의 이 PC 전용 프로필과 같은 방식, 출처 `local`). 직접 고치고 지울 수 있다.

## 테스트 목록

- 세트 하나가 곧 테스트 묶음이다. 세트 안에 묶음을 여러 겹 두지 않는다.
- AI에게 요청할 때마다 새 테스트가 세트에 **더해진다**. 지금의 '테스트 추가'가 기본 흐름이 된다. 새 초안이 기존 목록을 밀어내지 않는다.
- 테스트 id는 **세트 안에서 유일**하다(SC-n, TC-n 이어서 매김). 지금은 초안마다 SC-1부터 시작할 수 있어 쌓으면 겹친다.
- 분류는 태그로만 한다. 화면은 세트 전체를 태그·채택·실행 상태로 걸러 보고, 골라 실행한다(골라서 실행은 이미 있음).
- 코드는 테스트 추가 요청 단위로 나눌 수 있다. 다만 AI가 테스트를 더하거나 고칠 때 **다른 테스트의 코드를 다시 쓰지 않아야 한다**(지금의 덧붙이기·검사 규칙을 유지).

## 보낼 것

- 서버로 보내는 데이터의 형태는 아직 정하지 않았다. 형태가 정해지면 그 형태(파일·JSON)로 보낸다.
- 그때 한 곳만 바꾸면 되도록, 세트 데이터를 보낼 형태로 만드는 일과 배포 서버로 보내는 일을 **보내기 모듈 하나**에 모은다. 세트 폴더의 `tests/`(목록·코드·결과)가 그 입력이다.
- 형태가 정해지기 전까지는 지금의 '서버 전송'을 세트 단위로 옮겨 그대로 둔다(채택분 JSON, 세트 id, 버전 충돌 확인). 임시 형태임을 코드와 문서에 적어 둔다.

## 패널

- 위쪽 칩: 세트 이름. 누르면 세트 시트: 서버 세트 / 이 PC 전용 세트 목록, 각 세트의 대상 주소·버전·테스트 수. 세트 상세는 받은 정의(읽기 전용)와 내 설정(시작 URL·계정)을 보여 준다.
- 세트에 새 판이 있으면 세트 칩에 표시하고, 세트 상세에 바뀐 것과 **받기** 버튼을 보여 준다.
- 세트를 바꾸면 타임라인·테스트 목록·세션이 그 세트 것으로 바뀐다. AI 작업·테스트 실행 중에는 바꾸지 않는다(지금 도메인 전환 규칙과 같음).
- 테스트 목록 시트: 세트 전체. 태그 필터가 주 분류 수단이다.

## 기존 데이터 옮기기

- 지금 쓰는 프로필 하나 → 세트 하나(id는 프로필 id). 그 프로필 도메인의 수행 기록·보관본·초안·로그, `tests/suites/<도메인>/<프로필>--*.spec.ts`, 확장의 `suite@<도메인>`·`timeline@<도메인>`을 그 세트로 옮긴다.
- 같은 도메인에 프로필이 여럿이었으면, 묶음 id 앞부분(`<프로필 id>--`)으로 나눠 각 세트로 보낸다. 나눌 수 없는 것(수행 기록, 세션)은 그 도메인을 마지막에 쓴 프로필의 세트로 보낸다.
- Claude 작업 폴더 경로가 바뀌므로 옮긴 뒤 첫 대화는 새 세션으로 시작한다(대화 기록은 `~/.claude/projects/`에 그대로 남는다). 패널에 한 번 알린다.
- 옮긴 원본은 바로 지우지 않고 `.koa/migrated-<날짜>/`로 보관한다.
- 두 번 돌려도 같은 결과여야 한다.

정한 것(작성자 판단, 검토에서 나온 질문에 대한 답):
- **언제·누가**: 호스트는 도메인↔프로필 대응을 모른다(이 PC 전용 프로필은 확장에만 있다). 그래서 옮기기는 패널이 연결해 프로필 목록·활성 프로필을 보낸 뒤 호스트와 패널이 함께 한다. 도메인 데이터는 묶음 id 앞부분으로 가를 수 있으면 그 프로필로, 아니면 **그 도메인에 해당하는 활성 프로필**, 그것도 없으면 그 도메인 프로필 중 id 순 첫 번째로 보낸다.
- **어떤 테스트를 옮기나**: 확장의 `suite@<도메인>`(반영·코드·결과가 붙은 지금 묶음) 하나만 세트의 `tests.json`으로 옮긴다. 호스트 `drafts/`의 다른 초안은 합치지 않고 보관 폴더로 옮긴다. 그러면 옮길 때 id가 겹치지 않고, 코드 제목·결과·`--grep`을 다시 매길 필요가 없다. 이후 새로 더하는 테스트는 세트 안 가장 큰 번호 다음부터 매긴다.
- **서버 프로필의 세트**: 옮길 때 `.koa/store/profiles/<id>.yaml`로 서버 흉내 `.koa/store/sets/<id>.yaml`을 만들고 출처 `server`로 둔다(받기만 원칙 유지). 이 PC 전용 프로필은 이 PC 전용 세트가 된다. `profiles/` 종류는 옮긴 뒤 읽기만 남긴다.
- **이미 보낸 묶음**: 서버에 이미 보낸 묶음(`<프로필>--<해시>`)은 그대로 둔다. 세트는 세트 id로 버전 1부터 새로 보낸다.
- **공용 예시를 가리던 사본**: 서비스에 맞게 고친 `.koa/store/tags/qa-tags.yaml`은 버리지 않는다. 기존 테스트 태그가 그것을 기준으로 붙어 있으므로 `<세트 id>-tags`로 이름을 바꿔 그 세트가 참조하게 한다. `example` 프로필 사본도 같은 방식으로 이 PC 전용 세트로 남긴다.

## 그대로 두는 것

- 도메인 확인(멈춤 → 이동 / 그래도 진행), 골라서 실행, 작업 로그 형식(위치만 세트 폴더로).
- 서버 프로필 받기만, 내 설정은 시작 URL·계정.
- 공용 예시 `store/`는 git에 둔다. 단 `.koa/store/`의 같은 이름 사본이 공용 예시를 가리는 문제(지금 `example`, `qa-tags`)는 세트 정의로 옮기면서 없앤다: 공용 예시는 받은 세트가 참조할 때만 스냅숏한다.

## 만드는 사람에게 맡기는 것

- `tests.json`·결과 파일의 정확한 스키마, 실행 이력을 몇 번까지 둘지.
- 코드 파일을 요청 단위로 나눌지, 세트 하나에 한 파일로 둘지(위 '다른 테스트를 다시 쓰지 않음'을 지키는 한).
- 패널과 호스트 사이 테스트 목록 동기화 방식(전체 전송 / 바뀐 것만).
- 보관본(recordings) 보관 개수 규칙.
- 세트 시트의 세부 화면 배치.
